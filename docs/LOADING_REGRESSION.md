# 2026-09-28 加载故障修复

## 后续受控撤回：恢复单线路默认行为

以 fc94a8a 的直接请求为基准，取消 0beef3a 引入的 700ms 请求竞速、Promise.any 和后续持久化选线。
每次请求默认直连 Supabase，15 秒超时与基准一致；只有幂等读取发生网络错误或 5xx 后尝试一次 /sb。
写请求不重放、不跟随某次读取结果切换线路。图片恢复固定 Supabase URL。
保留正文超时、调用方取消、读取失败不覆盖任务缓存和服务端密码校验。

这会减少健康但超过 700ms 请求的重复流量；两条线路均不可达时仍可能等待较长时间，不能将其宣称为已经修复所有国内网络问题。
新增 /connection-check.html：只读取同域首页与访问校验，连续三轮展示结果，无依赖、无自动上传结果或写业务数据。
它用于无 VPN 的真实设备验收；开发环境 VPN 的测试不能代替此验收。

## 2026-09-28 第二阶段：单一站点入口与 Safari 应用壳

无 VPN 反馈表明 Supabase 直连在实际手机网络上更差，因此不再在两条外部线路之间切换：

- 生产环境的 Supabase 客户端基址固定为本站 `/sb`，REST、Storage 和 Auth 复用同一域名连接；本地开发继续直连 Supabase。
- 启动时不再 GET `/api/access`。首次设备直接显示口令表单，登录成功后保存本机提示；受保护的服务端接口继续检查 HttpOnly Cookie。
- 新增 Service Worker，只缓存公开应用壳和静态资源，明确绕过 `/api/*`、`/sb/*` 和所有写请求。成功访问一次后，Safari 可在入口短暂断线时打开最近应用壳和本地记录。
- Service Worker 的导航策略为 6 秒 network-first，失败后使用最近成功的 HTML；静态哈希资源使用 cache-first。

该方案减少浏览器需要建立的域名连接数，并改善再次访问的容错。首次从未成功打开的设备仍依赖托管入口，Service Worker 无法在安装前解决网络断线。

## 已确认的代码问题

- b307fb7 将访问校验截止时间从 8 秒改为 4 秒。本次线上 GET /api/access 有 4.08 秒的成功响应，旧代码会提前中止。恢复为 12 秒；返回用户仍先显示已有页面。
- 749ea12 起门禁只在挂载时校验，短暂失败后不会自动恢复。新增 15 秒重试、online 恢复、过期 GET 结果隔离，避免旧结果覆盖刚完成的登录。
- loadCloudDailyTasks 把请求失败和空任务列表都表示为 []，hydrateDailyAdventures 因此用默认 Day 300 覆盖成功缓存。失败现在返回 null，并保留上次完整日历；签到页可见时每分钟及网络恢复时重新读取。
- 0beef3a 的竞速在响应头到达时结束，正文未读取便取消另一条线路。fetchOnce 的计时器也只覆盖响应头。现在读请求在超时保护下完成正文再参与竞速；写请求不自动重放。
- 同域转发返回 HTML 时可能被当作成功结果；现在拒绝此类响应，继续等待数据库 JSON 线路。
- 15 分钟线路有效期原来仅在模块加载时检查。现在每次请求检查有效期，并传递调用方取消信号。
